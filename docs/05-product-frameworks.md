# 05｜需求洞察与 B 端产品化框架

> 系列：AI 应用笔记 · 05 ｜ 项目：阅记 / 源引 GEO / B 端中台经历
> 面向：AI 产品经理面试官，以及刚转 B 端或从 C 端转 B 端的同行
> 一句话：**需求洞察是减法——把用户的一句话拆成真实痛点，再用「价值 × 频次 × 可行性」砍掉不值得做的；B 端产品化是边界——先把"影响哪些端、存量怎么兼容、怎么回滚、怎么验收"说清，再谈功能。**

## 0. 先看结论

- **两个公式**：用户价值 = 新体验 − 旧体验 − 替换成本；商业价值 = 愿付价格 − 企业成本。好需求要让两个公式同时为正，只满足一个都不成立。
- **听 → 拆 → 选 → 定**：听原始诉求，拆真实痛点，用"价值 × 频次 × 可行性"做减法，最后写成含验收标准与边界条件的 PRD。
- **三张优先级工具分场景用**：从 0 到 1 用 KANO（先基本型），存量优化用"价值 × 成本"矩阵，向决策者解释资源分配用 RICE；它们是沟通工具，不是决策本身。
- **B 端边界四问**：影响哪些端 / 存量怎么兼容 / 怎么回滚 / 怎么验收。这四问写在 PRD 前面，能省掉后面一半的返工。
- **用配置覆盖差异，用规范控制复杂度**：B 端需求没有"全都要"的解法，产品化不是把功能做全，而是让业务方能自助。
- **边界**：B 端经历来自内部系统与客户交付，不公开内部文档、客户名称与实现细节；结果数字是我负责范围内的口径；我没有规模化 SaaS 商业化经验。

## 1. 两个公式：为什么"功能更多"不是理由

俞军在《产品方法论》里给了两个公式（公开方法，本文只做转述）：

- **用户价值 = 新体验 − 旧体验 − 替换成本**
- **商业价值 = 愿付价格 − 企业成本**

这两条几乎能解释所有"用户不换"和"需求被砍"：

- 用户不换，往往不是新体验不够好，而是**旧体验已经够用，替换成本又太高**；
- 需求被砍，往往不是用户不需要，而是**企业算不过账**（获客成本、交付成本、复购）。

**例子：阅记为什么止损。** 用户价值公式里：新体验（把纸质书笔记结构化）是有价值的，但旧体验（Notion / 飞书等通用笔记）已经能覆盖大部分，替换成本（导出、重新组织、换工具）不低；再叠加平台能力会持续抹平差异化，商业价值那头也算不过账。两个公式同时告急，继续投入就只剩"坚持"。

**例子：GEO 为什么要先免费诊断。** 旧体验是 SEO / 发稿 / 代运营，新体验是"诊断 + 可被引用的内容 + 回测"，但替换成本不低（要持续供给内容、要等周期）。所以产品设计上先做免费诊断、现场实测，把"尝试成本"降下来，再谈付费——这不是让利，是价值公式的要求。

## 2. 听 → 拆 → 选 → 定：需求处理四步

这四步是我在项目里实际用过的顺序，也是面试回答"你如何做需求分析"的骨架。

```mermaid
flowchart LR
  A["听<br/>访谈 / 客诉 / 行为数据"] --> B["拆<br/>5 Why / JTBD"]
  B --> C["选<br/>价值 × 频次 × 可行性"]
  C --> D["定<br/>PRD：用户故事 + 验收标准 + 边界 + 指标"]
  D --> E["一页架构 + MVP 看板"]
```

### 2.1 听：获取原始诉求，但别让用户替你设计产品

- **访谈与客诉**是需求的富矿，但用户说的是"处境和痛苦"，不是解决方案；
- **行为数据**比口头表达可靠：装了不用、用了不回来、回来只用一个功能，都是信号；
- **一线情报 > 关键词工具**：做 GEO 时，选题不是从热词工具里扒的，而是从客户每天在微信里问的问题里来的——"小规模纳税人能不能开专票"这种客户真实问法，才是 AI 搜索问题的原型。

《启示录》里有一个观点我一直在用：**不能依赖客户告诉你要打造什么产品。** 客户能告诉你他的问题，方案必须由产品、设计、工程一起共创。

### 2.2 拆：把"一句话"拆成"四层需求"

以阅记为例，用户的原始诉求是"我想把书里的划线拍照记下来"。如果照做，产品就是一个 OCR 工具，价值很薄。继续拆：

| 用户说的话 | 拆出来的真实需求 | 对应产品能力 |
|---|---|---|
| "拍照记下来" | 录入成本要低 | 拍照/框选识别，而不是手抄 |
| "记下来之后呢" | 要知道这句话在书里的位置 | 章节定位（目录 + 页边章信息 + 页码） |
| "碎片没法复习" | 要能按逻辑重组 | 划线句补全 + 金字塔结构化 |
| "想整体回顾" | 要能看见知识结构 | 思维导图 |
| "不想换笔记软件" | 要能进入已有工具 | 导出 / 迁移 |

**拆需求的方法**：5 Why（连问五个"为什么"直到触及真实动机）、JTBD（用户"雇佣"这个产品去完成什么任务）、以及一个很土但有效的办法——**把用户的原话逐句翻译成"可验收的产品行为"**。翻译不出来的句子，大概率是伪需求或还没想清楚的需求。

### 2.3 选：做减法，用"价值 × 频次 × 可行性"丢掉伪需求

- **价值**：不做会不会有人受损？做了用户会不会改变行为？
- **频次**：是每天/每周发生，还是一年一次？低频需求很难撑起一个产品；
- **可行性**：一个人做得出来吗？成本结构成立吗？

用这三条筛完，阅记的原始需求列表（30 多条）收敛到 4 个核心功能，其余全部列为"后续"。**砍需求不是不努力，是承认资源有限。**

### 2.4 定：PRD 要写到"可验收"

我的 PRD 至少包含四件东西：

1. **用户故事**：谁、在什么场景、要完成什么、为什么；
2. **验收标准**：怎么算做完了（行为 + 数据 + 边界）；
3. **边界条件**：什么不做、异常怎么处理、影响哪些端；
4. **指标**：上线后看什么，什么情况下算失败。

再加一页架构图和 MVP 看板，研发就能开始拆任务；没有这四件，PRD 只是"需求描述"，不是"可交付的契约"。

## 3. 三张优先级工具：什么场景用哪张

| 工具 | 适用场景 | 怎么用 | 局限（必须知道） |
|---|---|---|---|
| KANO | 从 0 到 1、要先保基础体验 | 先做基本型（没有会骂），再期望型（越多越满意），最后才是兴奋型 | 分类靠用户调研，主观且会随时间漂移；兴奋型很快变基本型 |
| 价值 × 成本矩阵 | 存量优化、资源有限、需要快速取舍 | 按"用户价值 × 实现成本"四象限排，高价值低成本先做 | 两轴都是估算；忽略需求之间的依赖与合规风险 |
| RICE | 多个需求池、要向上解释资源分配 | 用量化分数（触达 × 影响 × 信心 ÷ 投入）排优先级 | 估算偏差大；"信心"容易变成装饰；对 B 端的长依赖链、合规风险不敏感 |

我的实际用法是**组合**：先用价值公式判断值不值得做，再用矩阵筛出性价比高的，最后用 RICE 跟决策者沟通排序。**工具是沟通语言，不是决策本身**——排序结果出来之后，还要人来判断依赖、风险与时机。

## 4. B 端边界四问

B 端产品最容易出的问题不是"功能没做对"，而是"边界没说清"。一个看起来简单的需求，背后至少牵动四件事。

**决策 1｜每个需求先过边界四问，再写功能描述**

- **背景**：B 端需求的返工，大多不是因为功能没实现，而是因为"影响哪些端、存量怎么办、怎么回滚、谁验收"没在 PRD 前几行写清，后面以"需求变更"的形式回来。
- **取舍**：A. 先写功能、边界等开发时再补——出 PRD 快，但评审和实现阶段会反复返工；B. 先写边界、再写功能——前期慢一点，但评审能提前暴露冲突，实现阶段稳定。
- **结论**：选 B。边界四问固定放在 PRD 最前面，写不清就不进入排期。
- **代价**：需要提前拿到多端、存量、运维的信息，对产品经理的跨团队沟通要求更高；早期 PRD 会显得"没讲功能"，需要向业务方解释顺序。

### 4.1 影响哪些端

同一套规则要覆盖 Web、移动端、OpenAPI、第三方集成，各端的权限与数据口径必须一致，否则用户会在不同入口看到不同的结果。

**例子：组织架构调整中的权限方案。** 企业客户调整组织架构时，最敏感的是"谁能看到谁的薪酬与人事信息"。原权限模型无法表达"部门负责人"和"HRBP"在同一份数据上的不同可见范围。这个需求的产品难点不是"加一个角色"，而是：

- 权限要落到**字段级**，而不是菜单级——否则同一张表里，HRBP 会看到不该看的字段；
- 规则要**多端一致**——Web 端、多维表格、OpenAPI 不能出现三种表现；
- 上线要**可回滚**——权限出错就是事故。

最终方案一次上线、零回滚。复盘时我最大的感受是：B 端产品经理的价值，很大程度上体现在"提前把坑画出来"。

### 4.2 存量怎么兼容

已有客户的数据、配置、流程不能因为新功能而坏掉。新字段、新规则、新接口都要回答：老数据怎么办？老接口还调不调？灰度期间两边怎么共存？

**例子：薪酬档案的自定义字段。** 不同行业的薪酬字段差异巨大：金融客户要复杂公式与等级，制造客户要班次与计件，互联网客户要期权与调薪记录。如果每个客户都定制开发，产品会被拖垮。

解法不是"做一个万能表单"，而是抽象出**标准字段类型**（文本、数字、日期、公式等），并定义校验、默认值、可见性与引用规则，让客户通过配置表达差异；新字段体系必须兼容存量数据与老接口，上线后零客诉。这背后是一条 B 端产品的基本原则：**用配置覆盖差异，用规范控制复杂度。**

### 4.3 怎么回滚

上线后出问题，能不能快速恢复？这决定了很多需求该不该做、该怎么做：

- 能不能灰度？能不能按客户/按业务线开关？
- 回滚是回滚代码、回滚配置，还是回滚数据？回滚窗口多长？
- 回滚之后，已经产生的数据怎么处理？

在 B 端，**"可回滚"不是运维细节，是产品设计的一部分**。如果一个需求上线后无法回滚、影响面又大，那它就不应该在周五晚上发。

### 4.4 怎么验收

业务方怎么确认"做完了"？产品怎么确认"做对了"？验收标准要可观察、可测量，最好由业务方自己确认。

**例子：三大中台的产品化。** 我长期同时负责动态配置、流控、消息队列三个中台组件的 SDK 与 Web 平台。它们的共同问题是：能力很强，但业务方不会用、不敢用。我把每个组件都当作 B 端产品来做——不只交付 SDK，还交付 Web 管理平台、接入文档与自助排查能力：

| 组件 | 原来的问题 | 产品化改造 | 结果 |
|---|---|---|---|
| 动态配置 | 误删配置导致线上故障；历史版本不可查 | 历史配置保存与回溯、自助查询、配置—服务关系可视化 | 清理无效配置 1000+ 条，基本杜绝误删配置引发的线上故障 |
| 流控 | 规则变更要改代码并重新部署，平均 45 分钟 | SDK 侧自动识别流量并埋点，Web 端可视化配置与动态下发 | 配置生效从 45 分钟降到 2 分钟，保障 4 次大促零事故 |
| 消息队列 | 发布风险高、测试环境串通、超长延迟不支持 | 环境标识隔离、蓝绿灰度、资源全生命周期可视化、超长延迟消息 | 测试环境零串通，故障定位时长约缩短 50% |

衡量这些改造是否成功的标准，不是"功能多不多"，而是**业务方能不能自己完成接入、配置和排查**。中台的产品价值 = 业务方能自助。

## 5. 配置 vs 定制 vs 抽象

B 端产品化绕不开一个三角：客户要差异、研发怕定制、产品要做通用。我的判断标准是三条：

1. **这个差异能不能被枚举？** 能枚举的差异 → 做成配置项；不能枚举的 → 先不做，或者做成开放接口；
2. **变更需不需要发版？** 需要发版的配置化，价值有限；能动态生效的配置化，才是真的降低交付成本；
3. **业务方能不能自查？** 出问题时业务方能自己定位，配置化才算闭环；否则只是把定制成本转移给了客服。

**决策 2｜用标准字段类型 + 配置覆盖行业差异，而不是按客户定制**

- **背景**：不同行业对薪酬档案的字段需求差异巨大（复杂公式、班次计件、期权调薪），如果每个客户都定制开发，产品会被拖垮。
- **取舍**：A. 按客户定制——客户满意，但交付不可规模化、维护成本随客户数线性增长；B. 做一个"万能表单"——看似通用，实际谁都不好用；C. 抽象标准字段类型 + 配置——前期抽象成本高，但能覆盖可枚举的差异。
- **结论**：选 C。定义文本、数字、日期、公式等标准字段类型，以及校验、默认值、可见性、引用规则；客户通过配置表达差异，新字段体系兼容存量数据与老接口。
- **代价**：抽象没做好时配置会越堆越多，产品滑向"低代码平台"；抽象过度又会牺牲真实差异。上线后零客诉不代表覆盖了所有场景，只代表当时接入的客户没有受阻。

所以配置化的目标不是"能配"，而是**刚好覆盖可枚举的差异**：配置能力过强会滑向"低代码平台"，抽象不足又会被定制需求拖垮，两者都会让维护成本指数上升。

## 6. 商业可行性：好需求也要算得过账

《启示录》把产品风险分成四类（公开观点转述）：价值风险（用户会不会用/买）、可用性风险（会不会用）、可行性风险（做不做得出来）、业务可行性风险（销售、法务、财务等利益相关者是否支持）。大多数产品失败，不是做得不好，而是这四类风险解决得太晚。

两个来自真实项目的判断，以及一个由此产生的决策：

- **交付物要匹配客户的决策路径**。同样的诊断能力，报告形态和现场形态得到的客户反应完全不同：**体检卖不动，处方卖得动——转化瓶颈往往不是价值不够，而是交付物和客户的决策路径不匹配。**
- **B 端还要过"非产品"的关**：法务、财务、安全、采购的流程，往往比功能本身更能决定一个需求能不能落地。这些不是产品经理能单独解决的，但必须在立项时就被识别出来。

**决策 3｜把免费诊断的交付物从"报告"改成"现场实测 + 行动方案"**

- **背景**：早期 GEO 的免费诊断交付一份完整报告，客户看完说"哦，有意思"，然后没有行动。报告很专业，但没有进入客户的决策路径。
- **取舍**：A. 继续做更完整的报告——显得专业，交付可复制；B. 改成现场实测 15 分钟 + 直接给优化方案与下一步——转化更直接，但依赖人力、难以规模化。
- **结论**：选 B。诊断的价值不在"证明我很专业"，而在"让客户在 15 分钟内看到自己的问题，并知道下一步做什么"；报告降级为过程材料，不是交付物本身。
- **代价**：交付变成人力密集型，早期无法规模化；现场实测对演示环境与提问质量要求高；"报告"作为销售物料的专业性会被牺牲一部分。这是早期验证阶段有意接受的代价——先验证转化，再谈产品化。

## 7. 边界：这套框架不覆盖什么

- **B 端经历有保密边界**：内部文档、客户名称、系统实现细节不公开；文中结果数字（零回滚、零客诉、大促零事故等）是我负责范围内的口径，不代表全公司指标；
- **没有规模化 SaaS 商业化经验**：我做过内部系统与客户交付，没做过从 0 到 1 的规模化 SaaS 销售；本文的商业判断来自 0→1 项目的教训，不是成熟商业化方法论；
- **框架有适用边界**：KANO / 矩阵 / RICE 更适合有多个需求、需要排序的场景；对平台型、双边市场、强合规行业，判断维度会更多；
- **C 端与 B 端逻辑不同**：C 端可以靠一个爽点赢，B 端要在多角色、多端、多流程之间做平衡，不能直接套用；
- **没有统计意义上的验证**：这些是实践结论，不是实验结论。

## 8. 结论来源拆分

**我的实践结论（来自三个项目与两段 B 端经历）**：

- 听 → 拆 → 选 → 定的四步顺序，以及"把用户原话翻译成可验收的产品行为"的做法；
- 阅记的需求拆解（从"拍照记笔记"到 5 项产品能力）与"30 多条砍到 4 个核心功能"；
- 三张优先级工具的分场景用法与"工具是沟通语言"的判断；
- B 端边界四问，以及字段级权限、薪酬字段抽象、中台产品化的具体经验；
- "用配置覆盖差异，用规范控制复杂度"与三条判断标准；
- "体检卖不动、处方卖得动"、交付物匹配决策路径；
- 中台产品价值 = 业务方能自助。

**公开方法/资料（只做转述，未摘录原文）**：

- 用户价值公式、商业价值公式、交易模型——来自俞军《产品方法论》的公开观点；
- 四类风险、产品发现与技术清单、"不能依赖客户告诉你要打造什么产品"——来自《启示录》的公开观点；
- KANO 模型（狩野纪昭）、RICE 模型（Intercom）、5 Why / JTBD——都是公开的产品方法，本文写的是我的使用方式与局限判断；
- "先质疑需求、最后才自动化"的五步工作法——来自公开的马斯克五步工作法，我在 B 端需求评审里借用了它的顺序。

## 9. 如果重来

1. **每个需求先写边界四问，再写功能描述**——顺序反过来，返工会少一半；
2. **把"业务方能否自助"写进验收标准**，而不是上线后再补文档；
3. **更早做商业可行性的假门测试**：不要等产品做完才问"用户会不会付钱"；
4. **把"替换成本"当成一等公民**：无论 C 端还是 B 端，用户不换的理由往往比"你的功能不够好"更致命。
